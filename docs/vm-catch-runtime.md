# 阶段 2V：受限脚本 catch 运行时

## 一、结果与范围

依据[阶段 2U 静态语义](vm-catch-semantics.md)和[设计审计](vm-catch-evidence/runtime-design.md)，本轮实现普通函数的 `2c/1a/0e`，仅将 `19` 的整数/整数除零路由到脚本捕获。支持表为 **68 种限定操作码**；主语料 73 种中交集 66 种，缺 `05/06/10/17/35/36/45` 七种，合成路径额外含 `4d/4e`。这不是功能完成率，阶段 2 尚未完成。

公共 `Value`、`VmError`、`Completion`、`RunOutcome`、`VmLimits` 与调用 API 不变，没有新依赖或 unsafe。测试仍只执行内存合成程序；参考 ELF、启动脚本及原始业务字节码没有执行。

## 二、指令与错误来源

| 操作 | 实现与边界 |
|---|---|
| `2c` 注册 | 目标 `pc+1+signed_i16(a)`；检查函数边界，禁止恢复到已验证的可选参数初始化区。要求已进入普通函数，局部槽完整；保存帧 ID、帧深度、栈长度与目标 PC。捕获数量上限沿用 `max_stack`，这是 Rust 资源策略。 |
| `1a` 正常结束 | 仅弹出本帧拥有的最内层记录，不恢复值栈、不合成返回值。空表或跨拥有者结束为不可捕获 `InvalidProgram`，不消费值栈或捕获记录。 |
| `0e` 标记 | 独立压入整数 `1`，不要求前一步曾捕获错误，不生成错误对象；遵守普通栈上限。 |
| `19` 整数除零 | 两个操作数均为整数且右值为零时，在该失败位置标记私有 `IntDivZero` 来源；栈操作数尚未消费，再进入路由。无处理器时保持原 `Arithmetic` 错误和诊断现场。 |

注册原生证据为 `vm_newThreadCatch@0x080aaf84`，`ev_446aa83f597882387e0856507a84ad5ec466a2e91a4e234c7e9c000ca98eec9a`；结束为 `vm_endThreadCatch@0x080aae08`，`ev_3c2a03d9a2a44bb053d7549ec474236c098efdaddd7ead0a8a811d91c7507797`。`vm_caughtError@0x080ab020` 的汇编 `ev_9fb21c970e49e1948945a0156491b006ffff02c2dfe7da9caf0a8d96167cad97` 确认压入 1。

整数除零对应 `vm_divValue@0x0808e1a4` 的 `0x0808e27d` 零检查及 `0x0808e2ea CALL vm_error`，汇编 `ev_19597a6d356a5c98c32c16698ef7be5e4ad2201b7a0a22f7a714cc7918dd6f89`。来源标记不依赖 `VmErrorKind` 或诊断字符串，所以共享同一 `Arithmetic` 文本的 `MIN/-1` 溢出仍不可捕获。实数/混合除零、余数、复合赋值、返回验证、限额及内部状态错误也不进入脚本恢复。

完整记录复用[阶段 2U 函数索引](vm-catch-evidence/functions.md)和压缩证据；本轮没有新 REA 查询。原生空表结束直接递减计数，Rust 明确拒绝该损坏输入；原生整数溢出路径未见软件保护，Rust 明确返回错误。这两点是安全差异，不宣称对异常输入完全等价。

## 三、状态与资源恢复

`ScriptCatch` 是私有元数据，不持有容器、槽或帧的强引用。私有 `StepFault` 的错误诊断使用 Box，来源标记只存活于当前指令，避免粘性标记误归类后续失败；对外错误类型不变。

1. 选取最内层记录，预检拥有者身份、代码、对象、保存长度、函数存储边界及直接子调用边界。无记录则沿用原错误路径；无效恢复上下文在任何资源销毁前失败，不补造值或尝试外层恢复。
2. 跨函数时，先截断到直接子帧的 `bp-argc`，释放年轻调用参数、局部和临时项；再移除年轻帧。然后消费命中记录，截断到注册时长度，设置拥有者的处理 PC。同帧恢复仅执行后一阶段。
3. 真实 `StackEntry` 保留到边界以内，不能从公开栈快照重建。保留槽中的隐藏循环游标继续有效，年轻帧控制槽释放其数组头。共享数组/映射只释放离开范围的所有权；最后映射头析构仍清空成员槽。
4. 提交阶段没有用户回调、借用 guard、可失败分配或预算让出。引用租约索引只修剪失效项，存活成员/临时引用仍计入配额；退出帧的局部引用不能因栈位置复用而复活。

顺序依据 `vm_traceError` 的 `ev_3aa06be9e85308cb2db022171ebc8b97169c4291640f5d39b9176041544f81e4` 以及 `vm_doActions` 的 `ev_a280841df7ce885805c45ba2b70f60cf4628279d7dbb748b1f816ba99a1ad2c4`。普通 Rust 帧不包含完整原生对象执行引用机制，不能把该实现扩大为任意 efun、JIT 或线程兼容。

正常返回在验证返回值前移除本帧捕获，依据 `vm_returnFromFun@0x08094978`，`ev_6a8948bf446a008fa48fc2ecc8711a14fc41635f9cd05e4cfcdacf8bec7a6215`。失败转移只负责资源清理，之前完成的变量和容器写入不会回滚。

零预算不改变状态。错误指令占一次预算，恢复属于该步，下一条 `0e` 需要新的指令预算。成功重启清空旧捕获，启动预检失败保持原现场；finishAction 与整次任务清理同步清表。无处理器或不可捕获错误仍采用原粘性失败，保留真实出错函数、PC、偏移和操作数现场。

## 四、准备策略与未实现能力

初始化段直接拒绝三条 catch 指令；初始化/构造准备入口沿用保守策略，拒绝**任何链接函数体**中的 catch，包括静态未调用的 helper，并非精确可达性分析。运行时另检查生命周期任务边界。可选参数默认表达式仍限原线性白名单，正文可以在入帧后使用 catch；验证过的初始化区不能作为捕获目标。

本轮不支持生命周期内 catch、回调 catch、通用抛出、last-error 查询、新错误来源、线程或 JIT 恢复。不会用 `panic`/`catch_unwind`/longjmp 表示脚本异常。其他未实现操作码和准备校验失败继续明确拒绝。
