# 下一批 2AI：Bytes 比较与拼接定向取证

这是2AH审计选出的**下一批取证任务**，不是已完成取证或可直接放宽运行时的证明。对应G01、P01。本批2AH不打开反编译会话。

## 目标与固定范围

恢复01以及1c/2a/1e/20/25/27中Bytes相关操作数分支，形成首批“普通函数 Bytes 比较/拼接”的Rust实施规格。必须同时检查Bytes与非Bytes的混合输入如何处理；未实现分支必须列出，不猜测转换规则。

Buffer表示、成员索引/写入、范围引用、容器算术、非标量捕获、一般catch、Global init、真实efun/服务、调度与JIT不纳入本批实现设计。允许沿Bytes helper检查Buffer分流以确定边界，不据此扩展Buffer目标。

## 入口、证据复用和问题清单

从原始magic_Linux32及其固定SHA-256身份开始，先检查现有证据记录是否已覆盖所需分支，再决定最小补取范围。使用REA时按对应技能检查现有会话并保留完整Evidence、限制和出处，不从伪代码视图重建“原始C源码”。

| opcode | 原生入口（动作表地址） | 必答问题 |
|---|---|---|
| 01 | vm_addValue @0x0808e3b8 | Bytes在哪一侧接受何种tag？长度/分配、拼接顺序、NUL及非UTF8、临时共享和失败清理如何处理？ |
| 1c/2a | vm_eqValue @0x0808eed4 / vm_neValue @0x0808ef28 | 比较内容还是共享指针？长度/C终止规则？与Undefined/Void/数字等混合输入结果或错误？ |
| 1e/20/25/27 | 以docs/evidence/actions.csv对应条目为准 | 排序是否逐字节、字节是否有符号、前缀/嵌入NUL/大小写如何比较？调用的底层helper是什么？ |

复用包：vm-core-evidence/rea.json.gz、vm-numeric-evidence/rea.json.gz及vm-container-evidence/rea.json.gz；Function身份比较需保留2AF对vm_isEq的证据。已有包证明“有入口/某些分支”，不自动证明Bytes契约完整。跟进上表实际call target到字符串比较、长度、分配和释放helper；地址只从现有记录或本次返回取得，不预造helper地址。

Rust接点：numeric::binary（当前仅数值与含Function的身份分支）、Value::Bytes、Vm::step_instruction对应二元运算分支，以及失败定位/预算和现有catch来源分类。当前Bytes是Rc<[u8]>；是否可直接复用必须依据共享、长度和返回规则决定。

## 静态语料与实施规格交付

只读检查7,159个程序的相关指令位置，按Object/Global、init/普通函数、常量/局部值来源区分可确定与未知信息；可保存少量确定性导航样例。即使相邻指令压入字符串常量，也必须注明分析边界；普通opcode频次不能作为字符串运算次数或动态可达图。

交付原生结论账本（观察/推导/未知分开）、完整复用/新增Evidence与清单、可复算统计，以及下一轮Rust规格。规格必须锁定：接受的tag对、结果类型及内容、长度/NUL/混合转换、身份/共享、参数方向、错误类别与原始PC/offset、资源预检与提交、预算暂停、普通/Global上下文及catch隔离。

默认不新增公共类型/接口/依赖；若证据要求变化，规格须解释最小变更及兼容影响。本次2AH没有替下一轮决定这些尚未取证的语义。

## 退出条件与未来实现验收场景

- 每个所选操作码的Bytes分支及混合tag分支都能定位到完整Evidence/原始指令，未知项有明确阻塞及补取动作。
- 空Bytes、前缀、相同内容不同Rc、大小写、高位字节、嵌入NUL、长度边界、左右混合tag均有证据推导的期望表；不能套用Rust字符串运算猜期望。
- 未来合成测试覆盖成功与错误、共享输入不被意外改写、分配/栈限失败现场、单步/零预算、Object及Global调用者、现有数值/Function比较回归和catch不吞未实现分支。
- 当所选范围仍有关键未知时，只交付阻塞清单与继续取证规格，不以任意默认实现或少数示例宣告契约闭合。

原始ELF、包、脚本及历史证据保持不变；原生运行对照需要单独授权。实施阶段测试仍使用合成程序，不执行业务包代码。
