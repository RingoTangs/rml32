# 通用 catch 的 Rust 运行时设计审计（阶段 2U）

本文件是后续实现规格，不是已实现能力声明。阶段 2U 不修改公共 API、操作码白名单或运行时行为；现有 65 种受限操作码和 278 项 Rust 测试仍是基线。仅使用静态证据及当前源码，不执行参考 ELF、原始脚本或业务字节码。

## 一、已确认事实与设计边界

### 原生证据

原生栈向低地址增长，Rust `Vec` 向高索引增长；保存逻辑栈长度，不照搬 `sp` 的数值与比较方向。上述文本诊断不构成新增公开 `Value::Error`、脚本 last-error API 或完整错误分类的依据。

### 当前 Rust 事实

`Vm::run` 在每步前保存出错帧位置，错误后补全诊断，再进入构造回滚或粘性失败。普通失败保留栈便于检查。`return_function` 当前先验证返回值，再截断栈和退出帧，没有 catch 状态。`start` 验证成功后才替换旧执行现场；失败的启动不得破坏旧现场。

循环控制块藏于 `Cell::SlotPayload::Loop`，普通读取表现为 `Undefined`，其内部持有绑定引用与数组头。局部引用以单调帧 ID 与 `Weak<Cell>` 检验；对象引用依赖对象仍存活；成员/临时引用持有 `Rc<Cell>` 与可选配额租约。映射最后一个头释放时会清空成员槽，所以任何清理都不得跨容器头析构持有 `RefCell` 借用。

## 二、首批内部状态与接口（设计选择）

仅支持普通函数中的脚本捕获；初始化、构造、回滚析构及其可达 helper 暂不开放 catch。回调捕获、线程、JIT、宿主回调不纳入首批。准备阶段沿现有任务调用图校验拒绝上述路径，不等到运行中部分执行后才拒绝。

建议新增私有结构，字段不持有帧、槽、对象或容器的强引用：

```rust
struct ScriptCatch {
    frame_id: u64,        // 不能用可复用的 Vec 下标替代身份
    frame_depth: usize,   // 包含拥有者帧的长度
    stack_len: usize,     // 注册时逻辑栈长度
    target_pc: usize,     // 准备阶段验证后的本函数指令目标
}
enum StepFault {
    Runtime { diagnostic: VmError, site: RuntimeFaultSite },
    Fatal(VmError),
}
enum FaultDisposition { Handled, Unhandled(VmError) }
```

`RuntimeFaultSite` 是按具体错误产生位置登记的私有来源标记，首批允许列表固定仅 `RuntimeFaultSite::IntDivZero`，对应下节的原生 `vm_error` 与 Rust 失败点双向证据；后续扩展逐项取证。不能把现有 `VmErrorKind::Arithmetic`、`Bounds` 等整个枚举分组直接视为可捕获。新状态仅存在于私有 `Vm::catches: Vec<ScriptCatch>`；不向公开 `Value`、`Completion`、`RunOutcome` 或 `VmLimits` 添加字段/变体。首批注册数量沿用 `max_stack` 作为保守内部上限，并在注册前检查，明确这不是原生固定限制。

私有接口职责：`register_script_catch(target_pc)` 完成预检后单次提交；`end_script_catch()` 在非空且拥有者为当前帧时仅弹出栈顶记录；`retire_frame_catches(frame_id)` 在函数真正返回及其原生要求的验证时点使用；`route_fault(StepFault)` 只将已标记运行时错误交给脚本处理；`clear_execution_handlers()` 在成功重启、任务清理及执行终结边界使用。内部错误来源不改变现有对外 `Result<_, VmError>`。

禁止使用 `panic`/`catch_unwind` 或跨 Rust 栈的 `longjmp` 表示脚本异常。Rust 内存分配失败、非法内部状态、未实现能力和准备校验失败不伪装成脚本成功捕获。

### 首个可捕获失败位置：整数除零

| 对应位置 | 确认行为 |
|---|---|
| 原生 `vm_divValue`，`0x0808e27d` 检查整数除数，零分支 `0x0808e2e2` 到 `0x0808e2ea CALL vm_error`；正常分支 `0x0808e287 IDIV` | 整数/整数的除数 0 进入脚本错误路径，发生于实际整数除法前。反汇编 `ev_19597a6d356a5c98c32c16698ef7be5e4ad2201b7a0a22f7a714cc7918dd6f89`、反编译 `ev_8ae08d055f9314e0e074d8efe90e725516a1ec2a40a18b7fb1e9bc1014dc355c`，源档 `docs/vm-core-evidence/rea.json.gz`，本轮复用归档收录。 |
| Rust `src/numeric.rs:109` 的 `binary`，整数分支 `0x19` 的 `checked_div` | 除零与 `i32::MIN / -1` 目前同为 `Arithmetic` 且共用文本，故错误种类和错误消息均不能作为捕获判据。 |
| Rust `src/vm.rs:1785` 二元操作分支 | 先 `need(2)`、读取两个值、计算 `numeric::binary`，成功后才 `stack.pop()` 与 `set`。整数除零失败时两个操作数和其前栈槽仍在，除预增 PC 外未提交该步栈修改，可由保存长度安全收缩。 |

后续实现将二元分支中的两个值分别读取到局部变量，在失败来源仍明确的同一分支按 `opcode == 0x19 && matches!((left,right), (Value::Int(_), Value::Int(0)))` 标记 `IntDivZero`。`need`、读取与内部借用错误一律走 `Fatal`；其他二元错误仍走 `Fatal`。不从诊断内容倒推出来源，也不把混合实数除零、余数除零、复合赋值除零或返回类型错误自动加入允许列表。

`i32::MIN / -1` 原生此整数路径进入硬件 `IDIV`，没有对应的 `vm_error` 溢出分支证据；Rust 保持显式不可捕获错误，避免宿主硬件陷阱，这是已记录安全差异。无捕获器的整数除零保持原来对外 `VmErrorKind::Arithmetic` 及失败现场。

## 三、状态转移与资源清理

1. **注册**：准备阶段以受检整数运算计算 `pc+1+i16(a)`，验证目标属于当前真实函数体；运行时验证普通函数/已进入帧、保存长度覆盖当前帧所需存储、容量与 ID 有效。不得复制栈、值、循环控制块或引用租约。错误时不消费操作数、不创建半条记录。
2. **正常结束**：当前函数拥有非空栈顶记录时只弹出一条，不恢复保存栈、不压结果；正常路径结果由实际后续指令产生。原生无空表/拥有者校验，空表会把计数减成 -1；Rust 不模拟损坏计数。空表或跨拥有者结束返回不可捕获 `InvalidProgram`，且不改变帧、栈、catch 表，这是明确的安全边界，不宣称等价原生异常输入行为。
3. **可捕获错误**：先固定真实失败指令诊断，再选最内层合法记录；预检拥有者 ID、深度、目标和 `stack_len <= 当前长度`。不为恢复不足长度补 `Undefined`。确认所有需保留状态后，按下一段的两阶段次序清理年轻调用与拥有者临时栈，最后设置恢复帧 PC；未移动原记录前预检失败走不可恢复诊断。处理转移不回滚已经完成的变量或容器修改。
4. **进入处理分支**：`0x0e` 自己执行时压入整数 1；错误路由不提前压值，也不提供错误对象。该指令仍受普通栈容量检查。命中记录已移除，所以处理分支再次产生已允许的运行时错误交给外层捕获；若无外层按现有粘性失败保留诊断。
5. **正常返回**：先按照原生深度规则退休本帧的所有捕获，再进行返回值验证和既有返回处理；若验证失败且该位置已被允许捕获，只允许路由至仍存在的调用者捕获。当前函数已退休的捕获不可重新生效。既有成功返回值及 caller 上下文保持不变。
6. **预算暂停**：零预算及耗尽均不清理、不执行处理分支；捕获表随帧、栈、PC 保留。引发错误的指令占用一次现有预算；路由属于该步，下一条处理指令等待剩余预算或下次 `run`。不把宿主取消、预算耗尽变成脚本异常。
7. **无处理器/致命错误**：保留既有对外错误与诊断现场，禁止为了“catch 支持”统一清空普通失败栈；失败后不能恢复旧处理器继续运行。
8. **重启与生命周期**：成功 `start` 替换执行现场时同步清空旧 catch；验证失败不清空。`clear_task_frames` 同步清表；构造 primary/rollback errors 记录顺序和所有者对象删除规则维持原契约。消费 VM/释放 VM 时，私有记录不延长任何容器、帧或对象生命。`ActionFinished` 保持原完成现场契约，但不能令残留处理器在后续执行复活。

### 与原生顺序对应的两阶段展开

适用于已限定的普通解释函数路径：原生 `threadType==1` 的 `vm_errorQuit` 先调用 `vm_traceError(topEnv.funCp)`。后者先退休更深捕获，再调用 `vm_popNStack((funContext[toFunCp+1].argNum+bp)-sp)` 清理年轻调用栈，随后逐帧降低 `vm_funCp`、恢复当前上下文并处理执行引用；`longjmp` 之后，`vm_doActions` 才移除命中的记录、把拥有者帧剩余求值栈收缩到保存 `sp` 并设置目标。不是“先删除所有帧、再清空所有值”。

Rust 首批采用同样的资源先后关系，预检一次后提交：

1. 若拥有者不是最年轻帧，计算其直接子帧 `floor = bp - argc`；验证 `saved_stack_len <= floor <= stack.len()`。退休拥有者以上的捕获，先 `stack.truncate(floor)` 释放年轻调用参数、局部和临时槽，再 `frames.truncate(owner_depth)` 使退出帧身份失效。拥有者仍保留；同帧捕获跳过此阶段。
2. 从捕获表移除命中的记录，再 `stack.truncate(saved_stack_len)` 清理拥有者内新增的求值临时槽，设置拥有者 PC。不以正常返回方式调用 `return_function`，不做返回类型检查、不制造结果。

实现必须保证阶段间无脚本执行、预算让出、用户回调或可失败分配；路由作为同一步完成。普通 Rust 帧本身不持有容器强引用或原生对象执行引用计数，所以不能把 `frames.truncate` 声称为 `vm_unExecRefObject` 的完整实现。原生 efun、回调、JIT、线程类型差异以及 flag8 对 PCB 标志的处理排除在首批兼容承诺外。若后续加入帧退出回调或执行引用语义，必须重审此顺序。

### 清理的具体约束

- 用截断释放离开保存长度的真实 `StackEntry`，不能从公开 `stack()` 快照重建，因为快照把隐藏控制块投影成 `Undefined`。
- 丢弃帧 ID 使其局部引用立即失效；同一栈位置后来创建新帧也不能使旧引用复活。保留拥有者帧和保存长度以内的槽身份，不能克隆这些槽替换。
- 位于被截断槽中的循环控制块释放它持有的数组头及绑定租约；保留槽中的控制块继续保持原游标与共享数组，catch 不是循环重置。
- 只释放被丢弃值的 `Rc` 所有权；仍被变量或成员引用持有的容器/成员不能手动清空。映射最后一个头释放引起成员槽清空的既有行为仍生效；数组与映射不可混用相同析构假设。
- 无 `Cell`/映射借用 guard 跨截断或旧值析构。预检使用短借用，提交前释放；清理不能执行用户回调。
- `reference_cells` 仅是弱租约索引。部分展开后保留活租约条目并修剪失效项，不能像整次任务清理那样全部清空，否则仍存活的成员/临时引用会绕过配额计数。

## 四、未来实现的测试规格

所有运行用例使用合成程序，语料仅作静态解析：

| 场景 | 验收重点 |
|---|---|
| 正常结束、空表、错误目标、不同函数体目标、容量上限 | 与已确认语义一致，非法注册不改变栈/帧/表；正常结束不额外制造值。 |
| 同函数与跨一层/多层调用的 `Int/Int(0)`、操作码 `0x19` | 正确拥有者、PC、保存栈长度和整数 1；真实失败诊断不被处理器位置覆盖，原错误操作数未提前消费。 |
| `MIN/-1`、实数/混合除零、余数除零、复合除零及伪造相同 `Arithmetic` 文本 | 均不可捕获；证明来源依赖精确操作分支而非错误类别或字符串。 |
| 嵌套命中、处理器再次失败、内层正常结束 | 每次只消费正确记录；再次失败到外层；无外层保持粘性失败。 |
| 返回成功及返回数量/类型失败 | 当前帧记录先退休；错误不可被当前函数捕获；调用者处理器可按允许来源接收。 |
| 一步预算、零预算、处理指令前耗尽 | 分段运行与充足预算的最终结果/资源寿命一致，无自动重放错误指令。 |
| 循环控制位于保留槽/被展开年轻帧 | 前者保留游标，后者释放数组头和租约；无隐藏值泄漏或深复制。 |
| 数组/映射共享头、存活成员引用、临时引用 | 有效引用不丢，退出局部引用失效，配额恢复且保留租约仍计数；最后映射头析构行为符合旧测试。 |
| 处理前已完成的赋值、容器变更 | 展开只清理执行资源，不恢复旧业务值。 |
| UnsupportedFeature、内部不变量及未标记失败点 | 不被捕获，不隐藏未实现能力，保留旧诊断。 |
| catch 所在初始化/构造/回滚可达链、重启验证失败/成功、VM 消费 | 任务链在准备时拒绝；原 primary/rollback 顺序不变；成功重启清表，失败重启保持现场。 |

实施时保留全部既有 278 项测试；新增有行为差异的用例，不用“数据结构能 push/pop”的镜像测试代替语义证据。对资源寿命采用内部单元测试和现有私有计数钩子，不增加公开调试 API。

## 五、实现门槛与未确认项

注册目标公式、操作数宽度与正常结束行为现已由本轮 Ghidra 确认；空表/跨拥有者结束已锁定上述 Rust 安全边界。首个 `IntDivZero` 的原生/Rust 对应与错误前栈不变量现已闭合；实现允许列表只含这一项。后续新增失败来源仍须逐项证明原生错误路径及可恢复栈不变量。根报告及本轮函数清单是最终证据索引；不得仅据编译器常见 catch 模板填补失败来源。

`vm_traceError` 已证实承担上述解释线程路径的跨函数恢复；其他线程类型、回调 catch 与 JIT 环境关系，以及宿主错误文本查询路径，仍不能从此路径或 `vm_errorQuit` 的 longjmp 泛化。未闭合者明确保留为未知，首批准备器/运行时拒绝相关能力，不宣称完整原生异常兼容。本轮仅完成证据与设计，不将三个操作码加入支持表。后续只有完成上述合成运行测试、旧行为回归与资源寿命验证，才可将限定实现计入支持数。
